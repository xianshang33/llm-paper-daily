## 文章做了什么
- **背景**：当前智能体（Agent）开发主要依赖外部编排框架（如 LangGraph、CrewAI 等），这些框架在 LLM 之上通过每轮注入指令和路由决策来管理工作流。近期研究表明，对于程序性任务，直接将工作流放入前沿模型的系统提示词中（In-context）效果更佳，但这存在消耗上下文窗口、必须使用昂贵的前沿模型以及向第三方暴露专有逻辑等问题。
- **已有工作为什么解决不了**：虽然将工作流“编译”进小型微调模型权重（即“地下智能体”，Subterranean Agent）在理论上能解决上述问题，且已有研究（如 SimpleTOD, FireAct 等）证明了其可行性，但开发者仍倾向于使用编排框架。主要原因在于业界普遍存在三个认知障碍：认为编译后模型质量差、重新训练/编译周期太长缺乏灵活性、以及成本优势不明显。

## 文章的核心贡献点
- **提出了一个**：将智能体工作流编译进小型 LLM 权重的系统化评估与实证框架，旨在消除开发者对“编译式智能体”在质量、成本和灵活性方面的顾虑。
- **挑战1：质量差距**。人们担心小型编译模型无法达到前沿模型 In-context 学习的复杂推理和自然度水平。**解决方法**：论文通过在旅行预订、Zoom 支持和保险理赔三个复杂场景下的实证对比，发现 8B 规模的编译模型能达到前沿模型 87–98% 的质量，且在失败率上显著低于基于 LangGraph 的外部编排方案（例如旅行场景中 5.5% vs 24%）。
- **挑战2：灵活性与部署周期**。人们误以为修改工作流需要漫长的模型重训练过程，导致迭代缓慢。**解决方法**：论文证明在现代生产硬件上，重新编译周期仅需 30–50 分钟，这属于标准的 CI/CD 部署周期范畴，而非范式级的阻碍，从而证明了其具备快速迭代的工程可行性。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与数据集**：在三个真实场景中进行测试：旅行预订（14个节点）、Zoom 支持（14个节点，含产品特定知识）、保险理赔（55个节点，6个决策中心）。
- **质量对比**：
    - 在同等 3B 模型对比中，编译模型在 5 项质量指标中的 4 项上显著优于带有显式编排的基线模型 (p < 0.001)。
    - 扩展至 8B 模型后，编译模型在 Zoom 支持和保险理赔任务中达到了 In-context 前沿基线 87–98% 的质量水平，并匹配了基于大 70 倍的前沿模型构建的 LangGraph 编排器的性能。
    - 编译模型的失败率更低：旅行场景为 5.5%（编排器为 24%），保险场景为 9%（编排器为 17%）。
- **成本对比**：
    - 编译模型每次对话的成本比 In-context 基线低 128–462 倍。这一优势源于自托管带来的约 65 倍每 token 成本降低，以及约 2–7 倍的 token 用量减少（因为工作流不再占用 prompt）。
    - 随着程序复杂度的增加，由于编译模型的 prompt 大小恒定，成本优势进一步扩大。
- **延迟对比**：本地推理使得保险场景下的延迟降低了 2.8 倍。

#### 总结
本文通过实证研究打破了开发者对“编译式智能体”的三个主要误解。结果表明，将程序性知识编译进模型权重是处理持久性结构知识的自然解决方案：持久结构应存在于权重中，而瞬态状态应存在于 prompt 中。该方法以两个数量级的成本优势提供了接近前沿模型的质量，且具备敏捷的工程迭代能力，为替代昂贵且脆弱的外部编排框架提供了强有力的证据。
