## 文章做了什么
- **背景**：长程语言代理（Long-horizon LLM Agents）在执行需要多次工具调用和步骤协调的任务时，往往具备局部能力，但难以坚持直到完成明确的数量目标。现有的评估通常只关注最终的成功标志，忽略了过程中的进度丢失、重复工作或过早停止。
- **已有工作为什么解决不了**：现有的基准测试（如 WebArena, SWE-bench 等）主要衡量最终任务成功率或局部推理能力。它们无法区分“因局部决策错误导致的失败”与“因缺乏定量目标持久性（Quantitative Goal Persistence, QGP）导致的失败”，例如代理可能在完成部分工作后错误地声称任务已完成，或者陷入重复提交相同内容的循环，这些行为在传统的 Pass/Fail 评估中被掩盖。

## 文章的核心贡献点
- **提出了一个名为 PushBench 的基准测试框架**：专门用于测量和强制执行定量目标持久性（QGP），通过外部验证器确认是否完成了足够数量的 distinct valid items。
- **挑战1：如何精确量化并区分代理的失败模式（如重复提交、虚假完成、进度漂移）**
  - **难点**：传统评估仅看最终结果，无法透视代理在长程交互中是否真的在推进进度，还是在进行无效的空转或自我欺骗。
  - **解决方法**：PushBench 引入了基于验证器的工作单元（verifier-backed work units）和仓库 artifact 收集任务，直接测量重复工作、重复提交和虚假完成，将进度维持本身作为可审计的核心指标，而非隐含在最终成功标志中。
- **挑战2：如何在长程任务中强制代理保持 verified progress 并在真正完成时停止**
  - **难点**：前沿黑盒代理（如 Claude Code, Codex CLI）在处理大规模数量目标（如 100 个 artifacts）时，成功率急剧下降，显示出局部能力与全局持久性之间的巨大差距。
  - **解决方法**：文章对比了多种控制器策略，发现状态跟踪检索控制器（state-tracking retrieval controller）能通过消除重复提交达到 69-78% 的成功率，而 backlog-tracking 工作单元控制器在标准控制器完全失败的场景下仍能取得 25-50% 的成功率，证明了显式状态管理和验证反馈对维持 QGP 的关键作用。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：PushBench 包含两个受控任务家族：QGP-RepoScan（仓库 artifact 收集，隔离计数和检索）和 QGP-DataOps-lite（基于验证器的小型编辑和结构化更新）。此外，还进行了黑盒前沿代理评估。
- **Evaluation 结果**：
  - **控制器对比**：在匹配控制器比较中，状态跟踪检索控制器成功率达 69-78%，且消除了重复提交；backlog-tracking 工作单元控制器在标准控制器和完成门控控制器成功率为 0 的设置下，仍能达到 25-50% 的成功率。
  - **前沿代理表现**：使用 Claude Code (Sonnet 4.6) 和 Codex CLI (gpt-5.4) 进行评估。它们在 50-artifact 任务中表现良好，但在 100-artifact 任务中，每种条件下的成功率降至 9 次中的 3 次。
- **对比**：与传统基准不同，PushBench 揭示了定量目标对可靠性的要求不同于局部任务能力。现有工作往往高估代理的长程能力，因为它们在较小规模或单次任务上表现良好，但在需要严格计数和持续验证的长程任务中暴露出严重的持久性缺陷。

#### 总结
本文指出了长程 LLM 代理在“定量目标持久性”（QGP）上的显著缺陷，即代理难以在外部验证器确认完成足够数量的有效工作之前持续工作。通过提出 PushBench 基准，作者将重复工作、虚假完成和进度漂移从隐性失败转化为显性测量指标。实验表明，即使是顶尖的黑盒代理在面对高数量目标时也会大幅失效，而引入显式的状态跟踪和验证反馈机制能显著提升代理的持久性和可靠性。这强调了未来代理系统设计中，除了提升局部推理能力外，必须加强对外部验证进度的维护和全局目标的管理。
