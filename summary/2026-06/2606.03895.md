## 文章做了什么
- **背景**：大型语言模型（LLM）代理正从简单的请求-响应助手演变为长期运行的软件执行者。它们需要在多次模型调用间保持状态、分叉子任务、等待外部事件、请求人类授权、生成工具并执行必须可恢复和审计的副作用。
- **已有工作为什么解决不了**：现有的主流框架（如 ReAct, AutoGen 等）通常采用“聊天循环 + 面向模型的工具注册表”的抽象。这种设计将“动作可见性”与“资源权限”混淆，即模型可见的工具 schema 往往直接对应拥有主机文件系统、网络或凭证访问权的包装器。这种以工具分发为信任边界的设计在面对间接提示注入、工具输出注入以及需要动态权限管理的长周期代理时显得脆弱且不安全。

## 文章的核心贡献点
- **提出了一个 Agent libOS**：一种受库操作系统（Library-OS）启发的运行时底层架构，将代理视为具有身份、生命周期和显式能力的“AgentProcess”，而非简单的对话线程。
- **挑战1：信任边界模糊导致的安全风险**。现有系统中，模型调用的工具接口直接暴露主机资源权限，难以防止恶意注入或权限滥用。**解决方法**：Agent libOS 确立“运行时原语是权限边界”的核心设计规则，将工具视为类似 libc 的包装器，在文件系统访问、对象操作等原语边界处，基于显式能力（Capabilities）和策略进行检查，从而隔离模型意图与实际资源访问。
- **挑战2：长周期代理的状态管理与恢复困难**。长期运行的代理需要处理休眠、中断、人类审批及状态持久化，传统聊天循环难以有效管理这些系统级状态。**解决方法**：引入 AgentProcess 概念，提供进程身份、父子 lineage、类型化对象内存、检查点、事件队列和审计记录，支持异步调度、命名空间隔离及确定性恢复，使代理能像操作系统进程一样被调度和审计。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：作者实现了一个 Python 原型，包含异步调度、命名空间局部对象内存、运行时集成的人类审批、一次性权限授予、每进程工作目录、Shell 和镜像注册原语。此外，还实现了通过 libOS 系统调用代理支持的 Deno/TypeScript JIT 工具、文件系统/对象桥接工具以及可注入的资源提供者子系统。
- **Evaluation 结果**：论文侧重于安全性评估而非规划准确性提升。原型通过了 123 个回归测试，并提供了确定性演示和真实模型的冒烟测试脚本。评估证明了该运行时能够在不将工具分发作为信任边界的情况下，对长周期 LLM 代理进行调度、授权、恢复和审计。
- **对比**：与传统框架相比，Agent libOS 不再依赖脆弱的包装器约定来分离权限，而是通过系统级的能力控制和原语边界检查，解决了长周期代理中的身份、调度、资源权威、中断、隔离、恢复和审计等系统级问题。

#### 总结
Agent libOS 提出了一种新的 LLM 代理运行时范式，通过借鉴操作系统的进程和能力模型，解决了长周期代理在安全性和状态管理上的核心痛点。它将代理从简单的聊天循环中解放出来，赋予其明确的身份、生命周期和细粒度的权限控制，为构建安全、可审计且具备复杂交互能力的长期运行 LLM 代理提供了坚实的底层基础。
