## 文章做了什么
- **背景**：软件工程工具日益依赖基于大语言模型（LLM）的代理来定位需要修改的文件以解决软件问题。然而，大多数现有 AI 代理采用线性探索模式，即每一步只访问一个目录或文件。
- **已有工作的局限性**：现有的线性顺序探索方法（如 Agentless, SWE-agent, RLMs 等）在处理跨越多个子系统的多文件变更时存在结构性错配。单线程代理必须猜测起始点，如果步数或 Token 预算在第一个子系统中耗尽，后续包含关键文件的子系统可能永远无法被检查。此外，直接暴露原始文件系统访问权限可能导致导航错误和过度预测，从而降低准确率。

## 文章的核心贡献点
- **提出了一个非线性的、领域范围的并行代理探索框架（Domain-scoped parallel agentic exploration）**
- **挑战1：线性探索在多文件变更中的结构性限制**。难点在于当问题涉及多个子系统时，单一线程代理容易因预算耗尽而遗漏部分子系统。论文通过引入领域范围的并行代理生成机制，让小型模型（如 Haiku 类）同时探索不同领域，从而大幅提高了微 F1 分数，解决了单一视角的局限。
- **挑战2：原始文件系统访问导致的导航噪声与过预测**。难点在于无约束的目录遍历会使代理陷入无关的测试层级或过时路径，增加假阳性并消耗上下文。论文通过结构化并行探索而非 naive 的文件系统访问，减少了因测试文件过度预测导致的定位退化，并在不显著增加 Token 成本的情况下提升了召回率。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：以 Ansible 为例，使用 SWE-Bench Pro 作为初始基准，并构建了基于单个基础 commit 的 GitHub 问题持久会话评估方法。扩展基准包含了 2025 和 2026 年的最新 PR。
- **对比基线**：
    1. 无直接仓库访问的基础 LLM。
    2. 带有持久 Python REPL 的单代理递归语言模型（RLM）基线。
    3. 使用 Codex 5.5 High 的外部 CLI 基线。
    4. 较大的 Sonnet 纯 LLM 基线。
- **结果**：
    - 在 Haiku 类模型中，领域范围并行代理生成的微 F1 分数最高，且优势明显。
    - 在包含近期 PR 的扩展基准上，该方法仅次于庞大的 Codex 5.5 High，排名第二。
    - 在原始的 2020 SWE-Bench Pro 基准上，较大的 Sonnet 纯 LLM 基线通过预测较少文件获得了更高的精确度和微 F1，但其全金标准召回率（all-gold recall）显著较低。
    - **额外发现**：文档协同演化是一个未被任何方法解决的潜在依赖；强制的多代理咨询并未带来可衡量的帮助，反而大幅增加了 Token 成本。

#### 总结
本文指出了当前 LLM 代理在代码库探索中采用的线性模式在处理多文件变更时的结构性缺陷。通过提出一种非线性的、领域范围的并行代理探索方法，证明了即使使用较小的模型，也能在覆盖率和准确性上超越传统的线性探索基线。研究还揭示了原始文件系统访问的风险以及多代理咨询的成本效益问题，为未来构建更高效的软件工程代理提供了重要见解。
