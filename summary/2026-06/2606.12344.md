## 文章做了什么
- **背景**：以 OpenClaw 为代表的通用智能体正被广泛用于自主工具使用，但其在真实软件工程任务中的编码能力难以通过现有的 SWE-bench 标准进行准确衡量。
- **已有工作为什么解决不了**：现有的 SWE-bench 风格评估通常将提示模板、智能体循环、工具接口、超时设置等打包在一个特定系统中，导致评估结果混淆了大语言模型（LLM）、智能体 harness（即“claw”，指将 LLM 转化为智能体的框架）和任务实例这三个因果不同的因素。由于不同系统的 scaffolds、预算和终止策略各异，无法公平地跨系统比较 harness 的设计优劣，也难以归因性能差异来源。

## 文章的核心贡献点
- **提出了一个 Claw-SWE-Bench**：这是一个多语言的 SWE-bench 风格基准测试及适配器协议，旨在使异构的智能体 harness 在公平的设置下（包括固定的提示、运行时预算、工作空间契约、补丁提取程序和评估器）具有可比性。
- **挑战1：通用智能体无法满足 SWE-bench 的严格评分契约**。难点在于通用智能体本身不满足干净的 Docker 工作空间、补丁格式和预测契约要求。论文通过设计专门的适配器协议（adapter protocol），标准化了从原始智能体输出到符合评分标准的补丁提取过程，使得 OpenClaw 等通用 harness 能够参与公平评测。
- **挑战2：缺乏对 Harness 设计和成本效率的独立评估维度**。难点在于以往研究往往忽略 harness 选择对性能的巨大影响以及相似准确率下的巨大成本差异。论文将 harness 设计和成本核算作为一等公民进行评估，通过全量基准（350个实例）和轻量级基准（80个实例）揭示了 harness 选择对 Pass@1 的影响幅度（27.4个百分点）以及不同系统在 API 成本上的显著差异。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **数据集构建**：全量基准包含来自 8 种编程语言和 43 个仓库的 350 个 GitHub 问题解决实例，源自 SWE-bench-Multilingual 和 SWE-bench-Verified-Mini，并进行了未来提交清理。同时发布了 Claw-SWE-Bench Lite，包含 80 个经过成本和排名感知程序筛选的实例，用于快速验证。
- **评估结果**：
    - **Adapter 的重要性**：在相同 GLM 5.1  backbone 下，OpenClaw 使用最小化 direct-diff 适配器的 Pass@1 仅为 19.1%，而使用完整适配器则达到 73.4%，证明适配器设计对编码任务至关重要。
    - **模型与 Harness 的影响**：在 OpenClaw × 9 种模型的扫描中，模型选择导致 Pass@1 变化 29.4 个百分点；在 5 种 claw × 2 种模型的扫描中，固定模型下 harness 的选择导致 Pass@1 变化 27.4 个百分点。
    - **成本差异**：准确率相近的系统在总 API 成本上可能存在巨大差异，突显了成本核算在评估中的重要性。
- **对比**：不同于 SWE-agent、AutoCodeRover 等单一 harness 系统报告各自的整体数值，Claw-SWE-Bench 解耦了模型和 harness 的影响，提供了可复现的横向对比基准。

#### 总结
Claw-SWE-Bench 填补了通用智能体在仓库级编码任务评估上的空白，通过标准化适配器协议和严格的评估契约，实现了不同智能体 harness 之间的公平比较。研究结果表明，harness 的设计和适配器的质量对最终性能有决定性影响，且成本效率是评估中不可忽视的关键指标。该基准为未来开发高效、低成本的编码智能体提供了重要的参考标准和数据支持。
