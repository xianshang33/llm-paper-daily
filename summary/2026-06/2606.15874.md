## 文章做了什么
- **背景**：当前主流的 LLM Agent 框架（如 AutoGen, OpenHands）都将 LLM 置于“编排者”的核心地位，由模型决定下一步操作、工具调用及终止条件。这种设计在短任务中表现良好，但在长程任务（如多文件重构）中暴露出严重问题。
- **已有工作为什么解决不了**：现有方法将 Token 爆炸、控制流幻觉和完成不可靠视为实现层面的 Bug，试图通过更好的提示词、更长的上下文窗口或重试逻辑来缓解。然而，这些方法未能触及根本架构缺陷：将循环、分支和序列等确定性控制流工作分配给概率性系统。无论模型多强或提示词多好，都无法从架构上保证长程任务的可靠性，错误会在长序列中累积且无法被边界约束。

## 文章的核心贡献点
- **提出了一个 Agentic Programming（代理编程范式）**：该范式主张由程序 govern 所有控制流，LLM 仅作为其中的一部分（称为 LLM-as-Code），仅在需要推理或生成时被调用。
- **挑战1：控制流幻觉与执行路径不稳定**。难点在于 LLM 作为概率模型，在长序列中容易偏离预定逻辑或过早报告完成。论文方法通过将控制权收归程序代码，LLM 在每次调用中保持灵活性但无法改变程序的执行路径，从而从架构上杜绝了控制流幻觉。
- **挑战2：Token 爆炸与上下文冗余**。难点在于传统 ReAct 模式下上下文随步骤线性累积，导致关键早期信息丢失或窗口溢出。论文方法基于执行历史的调用树构建有向无环图（DAG），使得每次调用的上下文长度由调用深度决定而非步骤累积，有效控制了上下文规模并保留了必要的结构信息。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与案例研究**：文章通过计算机使用代理（Computer-use agents）的案例研究验证了设计的实用性。在该设计中，LLM 被封装为代码中的自适应组件，程序负责处理视觉操作序列的逻辑流转。
- **评估结果**：实验表明，Agentic Programming 显著提高了长视觉操作序列的稳定性。与传统让 LLM 自主决定每一步的框架相比，新方法在处理长程、多步骤任务时表现出更强的鲁棒性，避免了因上下文截断或逻辑跳跃导致的任务失败。
- **对比**：相较于 AutoGen 等主流框架依赖 LLM 进行全权编排，该方法在长 horizon 任务中展现了架构级的优势，证明了将确定性逻辑交给代码、概率性推理交给 LLM 的混合模式优于纯 LLM 驱动模式。

#### 总结
本文批判了当前 LLM Agent 框架中将概率模型用于确定性控制流的架构缺陷，提出了 Agentic Programming 范式。通过引入 LLM-as-Code 概念，将控制流完全交由程序管理，LLM 仅作为执行节点嵌入 DAG 结构中。这种方法从根本上解决了 Token 爆炸和控制流幻觉问题，为构建可靠、可扩展的长程 Agent 系统提供了新的架构思路。
