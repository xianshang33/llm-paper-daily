## 文章做了什么
- **背景**：自然语言到仓库级代码生成（NL2Repo）要求系统从自然语言需求文档构建完整的软件仓库。与函数级代码生成相比，该任务需要更长的规划视野、跨文件的稳定接口以及对跨文件不一致性的迭代调试。
- **已有工作的局限**：现有的方法难以同时处理长程规划、多文件间的接口一致性维护以及复杂的依赖管理，导致生成的代码在结构合理性和功能正确性上存在不足。

## 文章的核心贡献点
- **提出了一个名为 CodeTeam 的 LLM 驱动的多智能体框架**，将规划、决策和实现分离为不同且协调的阶段。
- **挑战1：复杂的全局规划与接口一致性**。难点在于需要从宏观层面设计软件架构并确保各模块间接口兼容。CodeTeam 通过多个 Architect 智能体起草竞争性的软件设计草图（SDS），并由 CTO 智能体评估、选择并规范化为机器可检查的合同（指定文件所有权、公共接口和依赖约束），从而解决该问题。
- **挑战2：依赖感知的代码实现与迭代修复**。难点在于在多文件生成中保持上下文边界并处理跨文件错误。CodeTeam 引入 Developer 智能体在依赖感知调度器下生成代码，利用轻量级 Git 进行协调，并由 QA 智能体运行测试以驱动迭代修复，确保代码的功能正确性。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：在基于合成的 SketchEval 基准和基于执行的 NL2Repo-Bench 基准上进行评估，对比了 CodeTeam 的提示工程（PE）和 supervised fine-tuning（SFT）变体与对应的 CodeS 变体。
- **主要结果**：
    - 在 SketchEval 上，CodeTeam (PE) 和 CodeTeam (SFT) 的整体 SketchBLEU 分别提高了 4.1 和 2.9 个绝对点数。
    - 在 NL2Repo-Bench 上，CodeTeam 取得了最高的平均测试通过率（PE 为 34.6%，SFT 为 42.3%），证明其设计改进转化为上游测试套件下的功能正确性。
- **消融实验**：项目特定的开发者分配和检索增强规划分别对 SketchBLEU 的提升贡献显著（相对提升分别为 9.9% 和 8.1%），而基于 Git 的协调提供了较小但一致的补充改进。

#### 总结
CodeTeam 通过引入角色分工明确的多智能体协作机制（Architect, CTO, Developer, QA），有效解决了仓库级代码生成中的长程规划和跨文件一致性难题。实验表明，该方法在代码结构质量和功能正确性上均优于现有基线方法，特别是检索增强规划和特定的资源分配策略对性能提升至关重要。
