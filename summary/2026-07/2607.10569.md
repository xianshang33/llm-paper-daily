## 文章做了什么
- **背景**：现代编码智能体（Coding Agents）暴露了多种工具接口，包括 IDE 原语（如 Read/Edit）、Bash 命令行以及模型上下文协议（MCP）的代码执行工具。业界关于哪种工具接口最关键存在三种相互矛盾的观点：有的认为专用 IDE 原语至关重要，有的认为仅 Bash 就足够，还有的主张用代码执行工具替代所有原生工具以大幅降低 Token 消耗。
- **已有工作为什么解决不了**：现有的研究从未在同一个测试 harness、使用相同的模型和提示词，并针对不同的任务机制（Regime）和智能体设计进行交叉对比。因此，领域内无法确定每种主张适用的具体条件，也无法判断这些观点是否真正矛盾。

## 文章的核心贡献点
- **提出了一个**：完整性干净的三臂消融实验框架（baseline / bash_only / code_only），在合成计算任务和 SWE-bench Mini 修改任务上，固定模型、harness 和提示词，跨越两种智能体（Claude Code, OpenAI Codex CLI）和两种任务机制进行交叉对比。
- **挑战1：如何解耦任务机制与智能体设计对工具选择的影响？**
  - **难点**：不同智能体的架构差异和不同任务类型（如纯计算 vs 代码修改）可能导致最优工具表面不同，单一维度的比较会产生偏差。
  - **解决方法**：通过构建 (任务机制 × 智能体设计) 的四格矩阵，严格控制变量，发现最便宜的工具表面是由任务机制和智能体设计共同决定的，而非由单一因素决定。
- **挑战2：如何准确评估工具限制对成本的影响，区分成功运行与失败运行的成本构成？**
  - **难点**：简单的平均成本可能掩盖了在特定失败轨迹上的高额开销，导致对工具效率的误判。
  - **解决方法**：引入条件成本分析（conditional-cost analysis），将成本差距定位到“注定失败”轨迹上的失败成本，而非成功运行中的每次编辑税收，揭示了主要成本信号存在于缓存调整后的成本中，而通过率在各工具表面间保持不变。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：研究使用了两个基准测试套件：用于计算任务的合成 Artifact 基准和用于代码修改任务的 SWE-bench Mini。实现了三个工具臂：基线（默认工具集）、bash_only（仅保留原生 bash 及 read/glob/grep，移除 Edit/Write）、code_only（仅使用单个 MCP execute_code 工具，禁用所有原生内置工具）。代码和基准测试 harness 已开源。
- **Evaluation 结果**：
  - 在四个（机制，智能体）组合单元格中，限制智能体仅使用 execute_code 工具在三个单元格中比其最便宜的丰富工具竞争对手更便宜或统计持平（在 Artifact/Claude 和 SWE-bench/Codex 上显著；在 Artifact/Codex 上方向性一致）。
  - 唯一的例外是 SWE-bench/Claude，其中 code_only 成本高出 14.4%（不显著），分析表明这源于失败轨迹的成本。
  - 所有单元格内的通过率在统计上是持平的，表明在当前评估的模型规模下，工具表面的改变不影响最终成功率，主要影响的是缓存调整后的成本。
- **对比**：与 SWE-agent 强调 ACI 原语的重要性、mini-SWE-agent 主张 Bash 足够、以及行业报告称 MCP 代码执行可减少 98-99% Token 的说法相比，本文证明了这些结论依赖于具体的任务和智能体组合，不存在通用的“最佳”工具表面。

## 总结
本文通过严格的交叉消融实验，解决了编码智能体工具接口选择的争议。研究发现，限制智能体仅使用单一的 execute_code MCP 工具通常在成本上更具优势或持平，且不影响通过率。最优工具表面的选择取决于任务机制和智能体设计的共同作用，且成本优化的关键在于缓存调整后的成本，特别是避免在注定失败的轨迹上产生高额开销。这一发现为未来编码智能体的工具设计提供了实证依据，强调了情境化设计的重要性。
