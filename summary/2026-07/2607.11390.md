## 文章做了什么
- **背景**：基础设施即代码（IaC）扫描器可以在部署前检测 Terraform 等 IaC 语言中的云配置错误，但修复这些 flagged 配置仍然主要依赖人工。虽然近期基于大语言模型（LLM）的修复方法可以处理部分问题，但往往存在幻觉（生成不支持的结构）或在未真正解决问题的情况下抑制警告。
- **已有工作的局限**：现有的 LLM 修复方法缺乏对工具上下文的 grounding（接地/锚定），容易 hallucinate 无效的 Terraform 构造，且无法有效判断何时因缺乏部署特定上下文而应停止自动修复并升级处理，导致声称的修复率与实际验证通过率之间存在巨大差距。

## 文章的核心贡献点
- **提出了一个名为 TerraRepair 的原型系统**：这是一个用于 Terraform 修复的工具接地（tool-grounded）LLM Agent，具备结构化的升级机制。
- **挑战1：LLM 在 IaC 修复中容易产生幻觉，生成无效或不受支持的配置结构。**
  - **难点**：Terraform 依赖于特定的 Provider Schema 和版本，LLM 仅凭训练数据难以保证生成的 HCL 代码符合当前环境的语法和语义约束。
  - **解决方法**：TerraRepair 通过查询已安装的 Provider Schema 并检索 Terraform 引用中的依赖上下文，将 LLM 的生成过程 grounded 在实际工具环境中，并在返回候选修复前重新运行扫描器进行验证。
- **挑战2：缺乏部署特定上下文（如 KMS 密钥、CIDR 范围等）时，LLM 倾向于编造看似合理但实际不可用的修复方案。**
  - **难点**：许多安全修复需要具体的环境参数，这些信息不在代码静态分析范围内，LLM 无法凭空获取，强行修复会导致错误。
  - **解决方法**：TerraRepair 引入了结构化升级机制，当检测到所需的部署特定上下文缺失时，Agent 会选择“升级”（escalate）问题而非伪造修复，从而避免了无效修复的产生。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：在两个专门设计包含漏洞的 Terraform 仓库上进行评估，使用 Checkov 和 Trivy 两种 IaC 安全扫描器，覆盖 AWS、Azure 和 GCP 云平台。
- **对比基线**：与控制的一次性（one-shot）LLM 基线方法进行对比。
- **主要结果**：
  - 在组合 AWS 基准测试中，TerraRepair 显著提高了扫描器验证的修复率：Checkov 从 26.6% 提升至 78.4%，Trivy 从 44.8% 提升至 72.4%。
  - 大幅缩小了“声称修复”与“验证修复”之间的差距：基线方法的差距为 44.8–73.6 个百分点，而 TerraRepair 将其缩小至 5 个百分点以内。
  - 在抽样语义审计中，根据多数投票协议，78.9% 的 TerraRepair 扫描器验证通过的 AWS 修复被标记为正确。

#### 总结
TerraRepair 证明了工具接地（tool grounding）可以显著提高基于 LLM 的 IaC 修复在扫描器验证下的成功率。通过结合 Provider Schema 查询、依赖上下文检索和结构化升级机制，它有效解决了 LLM 幻觉和上下文缺失问题。然而，研究也指出，缺失的部署特定上下文仍然是实现完全自主修复的主要知识边界。
