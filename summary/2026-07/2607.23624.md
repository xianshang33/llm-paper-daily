## 文章做了什么
- **背景**：在代理式软件开发（Agentic Software Development）中，第三方 API 路由器（如 LiteLLM、OpenRouter）已成为统一访问不同 LLM 提供商的常见中间层。由于编码智能体通常采用高自主性操作以减少交互开销，路由器位于智能体与上游提供商之间的可信路径上。
- **已有工作为什么解决不了**：现有的客户端权限机制假设 LLM 的输出是可信的，但路由器可以检查并修改每一个请求和响应，且目前缺乏机制来验证提供商输出与智能体最终执行的仓库级操作之间的一致性。这种控制缺口导致客户端安全措施在实践中可能失效，且其实际影响此前未经过实证测量。

## 文章的核心贡献点
- **提出了一个 SIDEL 框架**：用于轨迹记录、重放、注入和防御评估的实验框架，并构建了一个包含 400 个样本的精选数据集。
- **挑战1：路由器侧注入的隐蔽性与多样性**。难点在于攻击者可以在不改变上下文解释的情况下替换或追加恶意命令，甚至通过 LLM 润色使注入内容在分布上与正常输出对齐，从而绕过基于规则的检测。论文通过定义四个逐渐隐蔽的干预级别（L1 响应替换、L2 响应追加、L3 LLM 润色注入、L4 分布对齐注入）来系统化地模拟和评估这些攻击。
- **挑战2：现有客户端防御机制的有效性不足**。难点在于智能体的高自主性使其难以实时验证每个操作的语义安全性，且传统的白名单或事后审查难以应对经过精心伪装的注入。论文通过评估四种代表性编码智能体及两种缓解措施（白名单执行控制、LLM 审查），量化了防御缺口，证明了仅靠客户端手段无法完全恢复端到端的控制权。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：开发了 SIDEL 框架，支持对编码智能体的交互轨迹进行录制和重放，并实现了上述四种级别的注入攻击。实验评估了四种主流的编码智能体。
- **Evaluation 结果**：
    - 在没有额外缓解措施的情况下，所有被评估的智能体在所有注入级别下的防御成功率均为 0%。
    - 路由器侧的干预显著改变了仓库级的操作行为，且现有的客户端 safeguards 难以检测。
    - 引入客户端缓解措施（如白名单）和反应式审查（LLM Review）能提高抵抗能力，但未能完全恢复端到端的控制。
- **对比**：与以往主要关注提示词注入或模型本身安全性的工作不同，本研究聚焦于供应链中的“中间人”风险，实证揭示了 API 路由器作为非受信中介带来的具体安全成本，填补了该领域实证研究的空白。

#### 总结
本文通过实证研究揭示了第三方 API 路由器在代理式软件开发中带来的严重安全风险。研究表明，路由器侧的注入攻击能够轻易绕过现有的客户端防御机制，导致代码库被恶意修改。虽然客户端缓解措施有一定效果，但无法根本解决问题，因此文章呼吁需要在提供商侧建立输出完整性保证机制，以修复这一信任链缺口。
