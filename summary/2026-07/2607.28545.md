## 文章做了什么
- **背景**：大型语言模型（LLM）在代码编写、修补和搜索方面表现出色，但生产环境中的值班根因分析（RCA）要求更高。RCA 需要从模糊的用户报告出发，在事故发生数小时后，对嘈杂的指标、日志、追踪数据和源代码进行推理。
- **已有工作为什么解决不了**：现有的软件工程基准测试通常基于静态代码库和明确的失败测试用例，缺乏真实生产环境的动态性。现有的 RCA 基准（如 AIOpsLab, ITBench 等）在环境真实性、遥测接口支持、源代码访问以及人工验证评分等方面存在不足，无法全面评估 Agent 在复杂微服务架构下的诊断能力。

## 文章的核心贡献点
- **提出了一个 ORCA-bench**：这是一个具有高保真生产环境的基准测试，包含一个实时 OpenTelemetry 插桩的微服务系统（通过 Prometheus, Jaeger, OpenSearch 暴露6天的指标、日志和追踪数据）以及 1,079 个 RCA 任务。
- **挑战1：处理模糊输入与多源异构数据**。难点在于从非结构化的用户报告和海量 noisy 的遥测数据中定位问题。论文通过构建真实的微服务环境和多样化的任务设置（变化报告具体性、检测时间和并发故障），迫使 Agent 像真实 SRE 一样交叉验证代码与运行时数据。
- **挑战2：评估标准的客观性与准确性**。难点在于 RCA 结果往往没有唯一的“正确”代码补丁，而是需要判断诊断的合理性。论文引入了由专家 SRE 策划并签字确认的真实症状作为 Ground-truth，并使用 LLM-as-judge 进行初步评分，随后通过人类独立重新评分验证（Cohen's $\\kappa_w=0.90$），确保了评估的可靠性。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：ORCA-bench 提供了一个 50GB 的测试床，包含六天的系统数据。它支持通过 Grafana 访问真实的遥测接口，并提供完整的源代码访问权限。任务设计系统地改变了报告的具體性、从发生到检测的时间（TTD）以及并发故障场景。
- **Evaluation 结果**：在五个前沿 Agent 中，表现最好的模型在中等难度任务（现实输入设置）上的 RCA 准确率仅为 25.3%，在高难度任务上仅为 10.0%。即使是最先进的 Claude Fable 5 也存在显著差距。最弱的模型在 40% 的事故报告中产生了幻觉（给出了不可能的根因）。移除源代码访问会导致所有指标下降。
- **对比**：与 AIOpsLab、ITBench、OpenRCA 和 SREGym 相比，ORCA-bench 是唯一同时支持真实环境、完整遥测接口、源代码访问、症状与根因区分以及人工验证评分的基准。现有基准在这些维度上大多缺失或仅部分支持。

#### 总结
ORCA-bench 揭示了当前前沿编码 Agent 在生产级可靠性任务上的巨大能力缺口。由于真实生产系统比测试床更大、更动态且更具特异性，文中报告的差距仅是所需工程投入的下限。该研究强调，在将 Agent 安全地委托给生产可靠性之前，仍需大量的技术进步和工程投资。数据集已公开。
