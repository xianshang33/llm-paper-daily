## 文章做了什么
- **背景**：基于模型上下文协议（MCP）的 AI Agent 在执行 Git 提交签名、API 认证等加密操作时，通常将私钥存储在软件可访问的位置（如明文文件、环境变量或容器内存）。任何拥有足够读取权限的进程均可提取原始密钥材料。
- **已有工作为什么解决不了**：现有的三种密钥管理层级（明文存储、软件保险库、运行时隔离容器）均存在一个无法消除的结构缺陷：原始密钥在某个时刻必然存在于软件可访问的内存中。提示词注入可将工具调用转化为读取和窃取原语，导致密钥在几分钟内被泄露。纯软件架构无法从根本上消除此类暴露风险。

## 文章的核心贡献点
- **提出了一个**基于硬件密钥库（Hardware Keystore）的零信任 MCP 强制架构，通过 PKCS#11 接口将私钥完全 confinement 在硬件边界内（如 HSM、TPM、智能卡），主机仅通过不透明句柄获取加密结果。
- **挑战1：如何防止提示词注入导致的密钥窃取？**
  - **难点**：传统方案中密钥驻留内存，攻击者可通过注入指令诱导 Agent 读取内存或执行恶意工具调用从而导出密钥。
  - **解决方法**：实施硬件隔离，密钥永不进入 RAM。结合五层零信任强制栈（会话身份 SAGA、范围边界 Smax、语义验证 RAV、污点跟踪及硬件执行边界），确保即使 Agent 被注入，也无法获取原始密钥材料。
- **挑战2：如何在保证安全的同时实现内容感知的授权？**
  - **难点**：单纯的硬件隔离可能过于僵化，无法区分合法的签名请求与恶意的滥用请求，需在不暴露密钥的前提下验证操作意图。
  - **解决方法**：引入语义验证（RAV）和污点跟踪机制，在硬件执行前对请求内容进行上下文分析和完整性校验，确保只有符合策略的操作才能触发硬件内的签名运算。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：使用 SoftHSMv2 作为软件 PKCS#11 模拟器进行复现测试，并在嵌入式 TPM 2.0 (Infineon SLB9670) 上验证了即插即用行为。架构包含五层零信任组件：SAGA（会话身份）、Smax（范围边界）、RAV（语义验证）、污点跟踪和硬件执行边界。
- **评估结果**：针对源自 AgentDojo 的 12 种注入场景进行测试，涉及四种 LLM 模型（gpt-oss-120b, Qwen2.5-72B, DeepSeek-V4-Flash 等）。
  - **基线攻击成功率 (ASR)**：19.3% [95% CI: 14.3%, 25.4%]，表明现有方案极易受攻击。
  - **保护后 ASR**：0% [95% CI 上限 2.0%]，实现了完全防御。
  - **误报率**：在四个良性任务场景中为零误报。
- **对比**：相比传统的明文存储、软件保险库及容器隔离方案，该架构从根本上消除了内存中的密钥暴露，将攻击面从“密钥提取”转变为不可行的“硬件突破”，显著提升了安全性。

#### 总结
本文指出当前 AI Agent 密钥管理的结构性弱点在于密钥必然短暂存在于软件内存中，易受提示词注入攻击。作者提出了一种基于硬件密钥库的零信任架构，通过 PKCS#11 接口将密钥操作完全限制在硬件边界内，并辅以五层安全强制机制。实验证明，该方案能将提示词注入攻击的成功率从 19.3% 降至 0%，且无误报，为 AI Agent 的加密工作流提供了实质性的安全保障。
