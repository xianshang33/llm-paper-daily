## 文章做了什么
- **背景**：随着大语言模型（LLM）在软件工程中的深入应用，开发模式正从简单的提示辅助转向代理式开发（Agentic Development）。在规范驱动开发（SDD）中，规范不再仅仅是描述性文档，而是直接指导代码生成的可操作中间件。特别是在数据库迁移（如 Oracle 到 PostgreSQL）等复杂任务中，规范成为连接软件意图与具体实现的关键桥梁。
- **已有工作为什么解决不了**：现有的研究多关注单一 Agent 内部的代码生成质量或直接的源到目标代码翻译，往往假设规范是“Agent 中立”的通用 artifacts。然而，不同 LLM Agent 对同一规范的理解和解释存在显著差异，现有工作缺乏对跨 Agent 环境下规范可移植性（Specification Portability）的系统性评估，忽视了规范在不同 Agent 间传递时可能产生的语义漂移和质量退化问题。

## 文章的核心贡献点
- **提出了一个跨 Agent 规范可移植性的实证研究框架**：以 Oracle 到 PostgreSQL 的迁移为受控任务，系统评估了规范在不同 LLM Agent（如 Amazon Kiro, Google Gemini, GitHub Copilot 等）之间传递时的兼容性和性能表现。
- **挑战1：跨 Agent 传递导致的严重性能退化**。难点在于不同 Agent 的训练数据和推理机制不同，导致对同一规范的解读存在巨大偏差，直接传递往往导致代码生成失败。论文通过实验发现，例如 Gemini 直接消费 Kiro 生成的规范时，Token F1 仅为 0.035，SQL 语法有效性低至 2.33%，证明了规范非中立的特性。
- **挑战2：缺乏有效的规范适配策略**。难点在于如何在不重新从头生成规范的前提下，提升外来规范在目标 Agent 中的可用性。论文评估了重写（Rewriting）、压缩（Compression）和检索增强（RAG）等策略，发现重写能显著提升 Gemini 的表现，而检索增强摄入是唯一在 Gemini 和 Copilot 的帕累托前沿上均表现良好的通用策略，为解决跨 Agent 兼容性提供了具体路径。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：研究分为两个阶段。第一阶段评估了单 Agent 规范优先迁移管道，处理了 1,006 个 PL/SQL 文件，其中 623 个成功再生，380 个脚本在 PostgreSQL 16 中成功执行。第二阶段进行跨 Agent 实验，使用包含 1,802 个 Oracle 脚本及其对应 PostgreSQL 实现的数据集，涉及 Amazon Kiro, Google Gemini, GitHub Copilot, Claude Code 和 Cursor。
- **评估指标**：采用 Token F1、精确匹配、SQL 语法有效性、AST 精确匹配、AST 平均相似度和即时可运行性等多维度指标。
- **主要结果**：
    - 规范大小 alone 不能预测实现质量。
    - 跨 Agent 转移会导致严重的依赖 Agent 的性能下降。最差的案例是 Gemini 消费 Kiro 规范，各项指标极低。
    - **策略对比**：重写（Rewriting）显著改善了 Gemini 的性能；压缩（Compression）并未带来普遍收益；检索增强摄入（Retrieval-augmented ingestion）是唯一在多个 Agent 上均处于帕累托最优前沿的策略，表明其作为通用适配方法的有效性。
- **对比意义**：与传统假设规范通用的观点不同，本研究量化了“规范方言”的存在，并证明了针对特定 Agent 优化规范摄入策略的必要性。

#### 总结
本文揭示了在异构 SDD 工作流中，规范不应被视为 Agent 中立的 artifacts。跨 Agent 的规范传递存在显著的质量退化风险，且不同 Agent 对规范的解读具有特异性。研究建议在多 Agent 软件工程中，必须明确考虑规范的可移植性、Agent 特定的解释机制以及基于检索的访问策略。检索增强被证明是提高跨 Agent 兼容性的有效手段，为未来构建互操作性更强的 LLM 开发代理生态系统提供了重要依据。
