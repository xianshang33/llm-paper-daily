## 文章做了什么
- **背景**：大型语言模型（LLM）数据代理正成为操作数据的接口，用于生成SQL、调用工具和总结结果。然而，仅凭答案准确性不足以作为可靠性的信号，因为基准测试中正确的答案可能源于无效的计算过程。
- **已有工作为什么解决不了**：现有的评估主要关注最终答案是否匹配参考值，忽略了背后的计算逻辑。自然语言推理和自由形式的理由存在“结构差距”（Structure Gap），无法可靠地指定现实系统所需的算子级程序。这导致系统可能通过错误的过滤、连接或聚合得出巧合正确的答案，而这种“静默失败”风险在传统评估中被掩盖。

## 文章的核心贡献点
- **提出了一个 Trace Integrity（追踪完整性）**：这是一种部署可靠性标准，用于评估答案背后的计算是否明确、可执行、模式有效、算子忠实、可重放、答案一致且可审计。
- **挑战1：结构差距导致的计算不可靠性**。自然语言推理难以精确映射到数据库算子，导致即使答案正确，底层逻辑也可能错误。论文通过引入“执行契约”（Execution Contracts）来解决这一挑战，这是一种结构化工件，将用户意图与模式元素、算子计划、假设、可执行查询及验证状态绑定，确保计算过程透明且可审计。
- **挑战2：缺乏对“正确答案/无效追踪”风险的量化**。传统指标无法区分真实力与偶然成功。论文引入了 CAIT（Correct Answer / Invalid Trace）率，专门衡量仅基于答案的评估将计算不支持的输出计为成功的频率，从而揭示静默失败的风险。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：在 BIRD Mini-Dev 数据集上进行了实证演示，对比了 Direct SQL、Operation Summary + SQL 和 Contract-First SQL 三种方法。
- **评估结果**：
    - **答案准确率**：Direct SQL (20%)、Operation Summary + SQL (22%)、Contract-First SQL (24%)，整体较低且差异不大。
    - **追踪完整性通过率**：分别为 39%、43% 和 40%，显示大多数生成痕迹不符合完整性标准。
    - **CAIT 率**：高达 55%、59.1% 和 45.8%。这表明在半数以上的情况下，看似正确的答案背后是无效或不可审计的计算过程。
- **对比结论**：结果证明答案准确性、追踪有效性和静默失败风险是截然不同的评估信号。仅依赖答案准确率会严重高估系统的实际可靠性。

#### 总结
本文主张现实世界中的 LLM 数据代理不应仅通过输出是否匹配参考答案来评估，而应评估其输出是否有可审计的计算支持。通过提出 Trace Integrity 和执行契约，论文为解决结构化数据任务中的结构差距提供了具体方案，并强调 CAIT 率作为关键风险指标的重要性，旨在推动从“答案正确”向“计算可信”的范式转变。
