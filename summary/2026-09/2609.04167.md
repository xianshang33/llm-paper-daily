## 文章做了什么
- **背景**：随着大语言模型（LLM）在软件工程领域的进步，评估重点已从函数级代码生成转向仓库级智能体（如 SWE-Bench）。现有基准主要衡量生成的补丁是否通过功能测试，即是否解决了报告的问题。
- **已有工作为什么解决不了**：现有的仓库级基准（如 SWE-Bench）仅以“通过功能测试”作为成功标准，忽略了现实软件开发中至关重要的“审查约束”（Review Constraints）。在实际代码审查中，即使补丁功能正确，若不符合向后兼容性、异常语义或特定编码规范等由审查者提出的额外要求，也不会被接受。因此，仅靠功能测试会高估智能体满足完整修复需求的能力。

## 文章的核心贡献点
- **提出了一个 SWE-Gate 基准**：这是一个仓库级软件工程智能体基准，显式地同时评估功能正确性和审查约束合规性。
- **挑战1：如何量化和分离“功能解决能力”与“审查约束合规性”？**
  - **难点**：传统基准将两者混为一谈，无法区分智能体是没能修好Bug，还是修好了但风格/规范不对。
  - **解决方法**：SWE-Gate 从真实的 Pull Request 审查评论中提取审查约束，并合成仓库级修复实例。每个实例提供独立的功能测试和约束测试，以及不合规补丁和黄金补丁，从而实现对两种能力的显式分离评估。
- **挑战2：如何构建高质量且具代表性的审查约束数据集？**
  - **难点**：审查约束通常隐含在非结构化的自然语言评论中，且需要可执行测试来验证。
  - **解决方法**：文章构建了包含 303 个仓库级修复实例的数据集，涵盖 75 个不同领域的开源 Python 仓库。通过人工分析和合成技术，将审查评论转化为可执行的约束测试用例，确保评估的客观性和真实性。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：SWE-Gate 包含 303 个修复实例，覆盖 75 个 Python 仓库。提供了完整的复制包（代码、数据、实验结果）。
- **评估结果**：使用四种不同能力水平的 LLM 后端在统一的编码智能体框架下进行实验。结果显示，在 644 个通过功能测试的修复中，有 221 个未能满足提供的审查约束。
- **对比与发现**：这一结果揭示了功能成功与完全符合修复规范的成功之间存在巨大差距。与仅关注功能测试的现有工作（如 SWE-Bench）相比，SWE-Gate 证明了仅进行功能评估会显著高估智能体在仓库级修复任务中满足全部要求的能力。

#### 总结
SWE-Gate 填补了现有软件工程智能体评估中的空白，指出“通过功能测试”并不等同于“可接受的补丁”。通过引入基于真实审查评论的约束测试，SWE-Gate 更真实地反映了工业界代码合并的标准。实验表明，当前 LLM 智能体在处理隐含的非功能性约束方面仍存在显著不足，未来的研究需同时优化功能正确性和代码规范合规性。
