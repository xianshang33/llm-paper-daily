## 文章做了什么
- **背景**：生产环境中的大型语言模型（LLM）代理通常需要在多种模式下执行相同的逻辑，包括实时服务（低延迟流式传输）、异步后台任务（高容错性）以及高容量批处理工作负载（如评估和内容预生成）。以亚马逊的 Rufus 助手为例，它服务于数百万用户，需要同时支持这些具有不同服务等级目标（SLO）的模式。
- **已有工作为什么解决不了**：现有的 Agent 框架通常将工作流定义与特定的执行运行时紧密耦合。如果复用为流式传输设计的编排逻辑来处理异步或批处理任务，会导致阻塞式的同步执行模型，无法利用提供50%价格优惠的批量推理 API，且难以满足异步任务对持久性和重试机制的需求。

## 文章的核心贡献点
- **提出了一个绑定自适应的代理执行平台**：该平台将工作流定义与执行底层（Substrate）分离，允许开发者一次性定义类型化的数据流图，并自动编译适配到不同的运行时环境中。
- **挑战1：执行语义与运行时的耦合导致代码冗余和维护困难**。不同模式（实时、异步、批处理）通常需要重写代码以适应不同的运行时特性。**解决方法**：通过引入“可挂起图节点”作为核心抽象，将 LLM 推理表示为根据所选底层动态改变行为的节点（在线流式交付、异步持久重试、离线批量提交），从而实现无需修改工作流代码即可适配三种运行时。
- **挑战2：如何在保证输出质量一致性的前提下降低批处理成本并利用现有基础设施**。**解决方法**：平台将同一数据流图编译为进程内流式处理（实时）、AWS SWF 持久编排（异步）或 Apache Flink 分布式流处理（批处理）。实验验证表明，在不同绑定下输出质量无差异，且批处理执行成功利用了批量 API 定价降低了成本。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：该系统已应用于亚马逊的生产环境 Rufus 助手中。支持五种常见的编排模式：单次推理 RAG、迭代 ReAct、组合式 PreAct、条件路由和多代理深度研究。
- **Evaluation 结果**：
    - **输出质量**：在三种不同的执行绑定（实时、异步、批处理）下，未发现输出质量有任何可检测的差异。
    - **成本效益**：批处理执行使得每次查询的推理成本降低，符合公布的批量 API 定价标准（约50%折扣）。
    - **规模性**：系统能够在生产规模下运行，批处理路径与流式路径并行操作互不干扰。
- **对比**：相较于传统方法需要为不同模式维护 separate codebases 或强制异步/批处理任务使用低效的阻塞式流运行时，该方法实现了真正的代码复用和成本优化。

#### 总结
本文提出了一种针对生产级 LLM 工作流的 substrate-portable（底层可移植）执行方案。通过将工作流定义为独立于执行环境的数据流图，并利用编译技术将其适配到实时、异步和批处理三种不同的运行时底层，解决了现有框架中执行语义耦合的问题。该方案在亚马逊 Rufus 系统的实际部署中证明了其有效性，既保持了输出质量的一致性，又显著降低了批处理工作的推理成本，为大规模 LLM 应用的多模式部署提供了高效的工程实践参考。
