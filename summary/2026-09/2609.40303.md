## 文章做了什么
- **背景**：自主机器学习工程（MLE）Agent 在公共排行榜上取得了显著进展。为了解决长周期任务中的进度停滞和 LLM 原始能力有限的问题，现代 MLE Agent 通常部署在日益复杂的“ harness ”（辅助框架/机制）之上，包括多智能体编排器、专用的检索子智能体等。
- **已有工作为什么解决不了**：现有研究难以区分性能提升是源于 Harness 的设计改进还是底层 LLM 骨干模型的增强。此外，由于评估成本高昂（单次评估需数千 GPU 小时），现有基准测试往往在不同骨干模型和硬件下报告结果，且种子数少，导致难以公平比较 Harness 的实际贡献。同时，随着 LLM 具备直接读写文件和执行代码的能力，以及上下文窗口的扩大，传统 Harness 中许多用于弥补模型短板的机制可能已变得冗余。

## 文章的核心贡献点
- **提出了一个最小化 Harness 的编码 Agent 基线**：论文通过大规模系统性消融实验，论证了在拥有强大骨干模型的情况下，复杂的辅助机制层在编码 Agent 设置中是冗余的。
- **挑战1：如何解耦骨干模型能力与 Harness 机制的贡献？**
  - **难点**：以往研究中 Harness 的性能提升往往与骨干模型的迭代同步发生，且评估资源受限导致缺乏严格控制变量的对比实验，难以归因。
  - **解决方法**：在相同的时间预算和相同的前沿 LLM 骨干模型下，系统性地对比了开源的最先进复杂 Harness 与仅包含基本读写和执行原语的最小化 Harness 单会话 Agent，发现复杂 Harness 并无优势。
- **挑战2：验证复杂机制在长 horizon 任务中的必要性。**
  - **难点**：MLE 被视为长 horizon 问题，传统观点认为需要专门的记忆管理和多智能体协作来维持长期上下文和探索。
  - **解决方法**：利用支持百万级 token 上下文的现代 LLM，证明在单一会话中直接访问执行环境足以处理当前 MLE 基准测试的任务，复杂的搜索树、种群程序和记忆层级并未带来显著的绩效回报。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：研究基于 MLE-bench 标准测试平台，使用固定的一组任务（fixed30 set），设定 24 小时的时间预算。对比了多种主流 Harness（如 Malena, Arbor, AiScientist, MLEvolve, ScienceFlow）与最小化基线。
- **Evaluation 结果**：
  - 在相同的骨干模型（如 Kimi K3, GLM 5.2, DeepSeek V4 Flash, Gemma 4 31B）下，复杂的开源 SOTA Harness 在奖牌率（Medal rate）和平均百分位（Mean percentile）上均未显示出优于最小化 Harness 基线的统计显著优势。
  - 性能的主要驱动因素是骨干模型本身的能力，而非外部 Harness 的复杂性。
- **相关工作对比**：与软件工程领域（SWE-bench）的发现一致，即随着骨干模型变强，固定 backbone 下的 Harness 改进不再带来显著提升。本文指出当前在 MLE 基准上投入大量精力手工打造复杂 Harness 的回报率极低。

#### 总结
本文质疑了当前自主机器学习工程 Agent 设计中日益复杂的辅助框架（Harness）的必要性。通过严格的控制变量实验，作者发现当使用强大的前沿 LLM 作为骨干时，简单的、具有直接环境访问权限的最小化 Agent 在性能上与复杂的多智能体编排系统相当甚至更好。结论表明，当前的性能瓶颈在于模型本身的能力，而非辅助机制的缺失，建议在未来的 MLE 研究中将重点回归到提升骨干模型能力，而非过度工程化外部 Harness。
