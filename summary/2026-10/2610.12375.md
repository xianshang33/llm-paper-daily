## 文章做了什么
- **背景**：LLM Agent 在旅行规划、股票交易和 IT 事件分类等应用中日益普及，但其高度自主性缺乏有效监管，容易导致因幻觉、工具调用顺序错误或无限循环而产生的高昂成本，以及因误操作或沙箱逃逸带来的安全风险。
- **已有工作为什么解决不了**：现有的解决方案主要分为两类，均存在显著缺陷。一是事后评估（Post-hoc），即在运行结束后分析日志，此时计算资源已消耗且损害已造成；二是在线守护代理（Online Safeguard Agent），即使用另一个 LLM 监控每一步，这不仅增加了额外的延迟和成本，且小型模型难以检测大型模型的错误，同时忽略了步骤间的结构依赖关系（如拓扑结构），无法有效识别循环或乱序调用。

## 文章的核心贡献点
- **提出了一个名为 OnTrack 的实时流式监控机制**：该机制通过将 Agent 的执行过程建模为有向无环图（DAG），利用流式结构感知最优传输（Streaming Structure-Aware Optimal Transport）算法，在毫秒级时间内将当前执行轨迹与历史成功轨迹进行对比，从而实时预警或阻断异常。
- **挑战1：如何在极低延迟下实现高精度的实时结构匹配？**
  - **难点**：传统的语义相似度比较无法捕捉步骤间的依赖拓扑，而复杂的图匹配算法通常计算开销大，无法满足实时性要求。
  - **解决方法**：OnTrack 将 Agent 的步骤及其依赖关系映射为 DAG 节点和边，利用最优传输理论高效计算当前部分轨迹与参考轨迹之间的结构距离，实现了每步约 1 毫秒的快速比对。
- **挑战2：如何在不同数据可用性场景下保持监控的有效性？**
  - **难点**：实际部署中可能缺乏历史成功轨迹或工具 schema，导致监控缺乏参照系。
  - **解决方法**：论文定义了三种数据访问层级（完全参考、仅工具 Schema、无先验知识），并调整监控目标。在数据充足时检测计划违规；在数据受限时，专注于检测结构性异常如死循环、停滞和无新结果的重复工具调用，确保在不同约束下仍能提供有价值的干预。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实验设置**：使用 SWE-bench 轨迹进行评估，重点分析前 8 个步骤的表现。
- **对比结果**：
  - **排名性能**：基于前 8 步，OnTrack 在区分失败轨迹和成功轨迹方面的表现优于基于内容相似度的方法，AUROC 提升了 0.057。
  - **成本节约**：引入中止策略（Abort Policy）后，节省了约 18% 原本会浪费在失败运行上的计算资源。
  - **准确性**：在中断的运行中，83% 确实指向失败（6 次中断中有 5 次是正确的），证明了其干预的高精确度。
- **相关工作对比**：相比“LLM-as-a-Judge”的事后评估，OnTrack 能在损害发生前干预；相比额外的守护 Agent，OnTrack 无需额外的 LLM 推理调用，显著降低了延迟和成本，并能捕捉结构层面的错误。

#### 总结
OnTrack 提出了一种创新的轻量级实时监控方案，通过结构感知最优传输技术解决了 LLM Agent 执行过程中的成本和安全隐患。它不仅在速度上达到了毫秒级响应，还在不同数据可用性的场景下展现了灵活的监控能力。实验证明，该方法在早期识别失败轨迹方面优于传统语义匹配方法，并能有效节省计算资源，为 LLM Agent 的安全部署提供了高效的工程化解决方案。
