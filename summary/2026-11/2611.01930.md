## 文章做了什么
- **背景**：大型语言模型（LLM）智能体通过命令行操作 Web 基础设施，并依赖于一个“返回假设”（Return Assumption），即每个工具调用都会在有限时间内返回，且请求的操作已完成。然而，许多命令在执行前会提出问题（如确认提示、密码输入等）。
- **已有工作为什么解决不了**：现有的智能体框架（Harness）在处理此类交互式命令时存在缺陷。如果关闭输入流，程序可能在未执行实际操作的情况下返回状态码 0（假成功）；如果保持输入流开放（如终端模式），程序会等待用户输入直到超时，导致智能体浪费大量时间和 Token，并可能因超时而误判任务失败。现有研究未能量化这一假设的失效情况，也未提供有效的修复机制。

## 文章的核心贡献点
- **提出了一个名为 RECEIPT 的系统**，用于测量和修复 LLM 智能体在 Web 服务操作中的返回假设问题。
- **挑战 1：静默失败与假成功**。当输入流关闭时，需要交互的命令可能直接退出并返回成功状态码，导致智能体误以为操作已完成。**解决方法**：RECEIPT 保持输入流开放，并通过系统调用监控进程状态，识别进程是否正在等待输入，从而避免将未执行的命令误判为成功。
- **挑战 2：资源浪费与超时误判**。当输入流保持开放但无自动响应机制时，命令会等待直至超时，造成 Token 消耗激增和任务延迟。**解决方法**：RECEIPT 读取进程等待的具体内容（如提示符），并通过经过模型检测验证的协议将这些状态信息返回给未经修改的智能体，使智能体能够及时提供正确输入，显著减少等待时间和 Token 消耗。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **数据集与基准测试**：收集了 91,469 次生产环境工具调用和 89,047 条公共智能体轨迹。构建了 Litmus（包含 158 个已验证的命令行调用目录）和 Tripwire（包含 25 对任务，区别仅在于是否有问题守护请求的操作）。
- **测量结果**：在 Litmus 测试中，关闭输入导致 11.5% 的测试调用在未执行请求操作的情况下返回状态 0；8 个主流框架中有 7 个在未连接终端时会关闭输入。在 Tripwire 测试中，未回答的问题使 Token 使用量增加 2.9 倍，且输入连接方式可将 Llama-3.3-70B 的排名从第 7 位提升至第 3 位。
- **RECEIPT 效果**：相比关闭输入的方式，RECEIPT 将虚假成功声明减少了 73.5%；相比普通终端模式，Token 使用量减少了 24.4%。它能以 85.0% 的准确率报告等待状态且无误报。在商业智能体运行时中，每次 Shell 调用的检查中位数耗时不超过 0.54 毫秒。
- **对比**：现有框架要么导致静默失败，要么导致高昂的超时成本，而 RECEIPT 通过精确的状态反馈解决了这两者之间的矛盾，提升了智能体的可靠性和效率。

#### 总结
本文首次量化并修复了 LLM 智能体在命令行操作中的“返回假设”问题。研究表明，智能体的可靠性不仅取决于 LLM 本身，还取决于其框架允许观察到的工具执行状态。作者建议智能体构建者应报告工具调用的实际执行情况而非仅返回状态码，基准测试维护者应在排名 LLM 之前修复并公开输入连接的处理方式。RECEIPT 通过监控系统调用状态并提供结构化反馈，有效消除了假成功并降低了资源消耗。
