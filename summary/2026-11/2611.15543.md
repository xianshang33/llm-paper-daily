## 文章做了什么
- **背景**：随着大语言模型（LLM）应用的普及，开发者常使用翻译器或兼容层在不同提供商的 API 之间转换对话请求。然而，API 的兼容性并不保证对话信息的完整保留。
- **已有工作的不足**：现有的模式验证（Schema Validation）仅检查结构合法性，无法检测语义信息的丢失；基于参考的差异测试需要额外的模型调用或参考翻译，成本高且难以区分是翻译错误还是目标 API 的能力限制。因此，静默的信息丢失（如指令角色、工具交互、错误状态等被篡改或丢弃）难以被传统方法检测。

## 文章的核心贡献点
- **提出了一个名为 isloss 的确定性测试预言机（Oracle）**，用于检测 LLM API 翻译过程中的对话信息保留情况。
- **挑战1：如何在不依赖参考翻译或额外模型调用的情况下，准确区分合法的表示变化与有害的信息丢失？**
  - **难点**：不同 API 格式存在结构性差异，简单的字段映射无法判断语义是否等价，且传统差分测试成本高昂。
  - **解决方法**：isloss 将源请求/回复和目标请求/回复映射到统一的中间表示 ConvIR，并应用显式规则来识别信息是否丢失，无需参考实现。
- **挑战2：如何区分可避免的翻译错误与由目标 API 固有局限性导致的退化？**
  - **难点**：某些信息丢失是因为目标 API 本身不支持特定功能，而非翻译器 bug，混淆两者会导致误报。
  - **解决方法**：通过规则明确界定哪些损失是翻译层应避免的，哪些是目标 API 能力边界导致的，从而精准定位翻译层的缺陷。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与评估方法**：通过基于规范的故障注入、人工审查以及对现有翻译器、网关和客户端库的实验进行评估。
- **主要结果**：
  - 在保留测试集中，isloss 检测出 125 个植入故障中的 95 个（76.0%），假阳性率仅为 2.0%（100 个允许变化中仅 2 个误报）。
  - 对五个翻译代码库的六种配置进行测试，发现 685 个完成翻译的请求中，有 127 个（18.5%）虽然通过了静态目标检查，但静默地改变了指令、角色或工具信息。
  - 在回复流处理中，36.4% 的翻译回复流导致至少一个官方 OpenAI SDK 出现异常或静默损坏。
- **对比与影响**：与传统验证方法相比，isloss 能发现那些“结构合法但语义受损”的隐蔽错误。行为实验表明，这些翻译引起的变化会显著改变模型在依赖受影响信息的任务中的表现，证明了对话保留是 LLM 互操作性的独立正确性要求。

#### 总结
本文揭示了 LLM API 翻译中普遍存在的静默信息丢失问题，并提出了 isloss 这一轻量级、确定性的检测工具。研究证明，成功的 API 翻译不等于对话信息的完整保留。isloss 为提升 LLM 互操作性、Agent 执行可靠性及模型评估的准确性提供了实用的基础保障。
