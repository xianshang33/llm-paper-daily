## 文章做了什么
- **背景**：构建智能体（Agentic）应用需要整合大语言模型（LLM）操作、工作流结构与应用状态，以及模型引导的路由。目前开发者通常使用 SDK 或代理框架，通过大量胶水代码来连接这些组件，包括准备模型输入、传播状态和分派模型选择的步骤。
- **已有工作的局限性**：现有的 SDK 和框架将执行逻辑分割在应用代码和框架内部之间。这种分离导致编译器无法看清控制流和状态依赖，阻碍了自动优化。此外，工作流的任何变化都需要协调更新大量的支持代码，显著增加了开发和测试的负担。

## 文章的核心贡献点
- **提出了一个名为“Agent-Native Programming”（代理原生编程）的新范式及其实现语言 Jac**：Jac 是 Python 的超集，通过统一的执行语义将 LLM 操作、工作流结构和模型路由紧密结合。
- **挑战1：开发复杂度高与代码冗余**。传统方法中，LLM 调用、状态管理和路由逻辑分散且耦合紧密，导致大量样板代码。**解决方法**：Jac 引入了 `by llm()` 构造用于类型化的模型操作和工具使用，以及“对象空间编程”（Object-Spatial Programming）来管理工作流结构和状态，从而将 AI 集成代码量减少了 1.8-8.7 倍。
- **挑战2：缺乏编译器可见性导致无法自动优化**。由于逻辑分割，编译器难以分析模型决策与程序执行之间的依赖关系。**解决方法**：Jac 引入了 `visit ... by llm()` 构造用于模型引导的路由，该构造从可执行的工作流步骤中衍生模型的选择并调度选定的步骤。这种模型决策与程序执行之间的显式连接为编译器和运行时提供了共同的依赖分析基础，实现了如推测执行和服务分区等自动优化。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现**：Jac 语言作为 Python 超集实现，包含特定的语法扩展以支持代理原生特性。
- **评估结果**：在五个基准测试和五个基线方法的对比中，Jac 相较于 OpenAI SDK，实现了 1.8 到 8.7 倍的 AI 集成代码减少。同时，它在观察到的任务质量上具有竞争力，并降低了编码代理的开发工作量。
- **案例研究**：两个案例研究展示了仅通过配置即可实现推测执行和服务分区，利用程序分析和运行时检查在特定条件下保持工作流行为的一致性。

#### 总结
本文针对当前智能体应用开发中存在的代码冗余和优化困难问题，提出了 Agent-Native Programming 范式及 Jac 语言。通过统一 LLM 操作、工作流和路由的执行语义，Jac 不仅大幅减少了开发所需的胶水代码，还通过增强编译器对控制流和状态依赖的可见性，开启了自动优化的可能性。实验表明，该方法在保证任务质量的同时，显著提升了开发效率和系统性能潜力。
