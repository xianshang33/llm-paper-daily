## 文章做了什么
- **背景**：大型语言模型（LLM）解码器在硬件实现中涉及跨时间步的状态传递。如果硬件中的状态更新错误，可能导致当前令牌输出正确，但随后几个令牌的输出被破坏。这意味着设计可能通过简单的输出测试，但实际上存在隐蔽的错误。
- **已有工作的不足**：现有的基准测试通常仅关注最终输出是否正确，缺乏对内部存储状态的细粒度验证。这种“黑盒”测试无法捕捉由状态腐败引起的延迟错误，导致评估结果过于乐观，且无法指导Agent如何调试复杂的硬件状态逻辑。

## 文章的核心贡献点
- **提出了一个名为 AIChipBench 的基准测试框架**：用于评估 LLM 编码 Agent 在自动化 AI 加速器设计（特别是 RTL 代码生成）方面的能力。该基准要求 Agent 实现量化后的 Qwen3.5、Gemma 3/4 和 Llama 3.2 解码器，并针对指定每一步输出和存储状态的可执行整数参考模型进行开发。
- **挑战1：隐蔽的状态错误难以通过传统测试发现**。由于状态错误具有滞后性，仅检查输出会导致假阳性。**解决方法**：AIChipBench 引入了暴露存储状态不匹配的调试反馈机制。研究表明，提供第一个状态不匹配的位置信息，相比仅仅提供输出反馈，能将所有 Agent-任务组合的接受率提高 25.0 到 46.9 个百分点，并将每个成功设计所需的 Agent 小时数减半。
- **挑战2：现有测试用例不足以泛化到真实场景**。许多在开发测试中通过的设计在未见过的数据上会失败。**解决方法**：基准测试采用了严格的隔离评估流程，包括在保留的令牌序列、重置条件、内存停滞情况以及综合（Synthesis）阶段进行测试。结果显示，在公开测试中接受的 69 个设计中，有 45 个在新的评估条件下于 32 步内失败，证明了超越开发案例的最终测试的必要性。

## 实现与部署，evaluation 结果，要有和相关工作对比
- **实现与部署**：实验涉及四个主流编码 Agent（Sol 5.6, Fable 5.1, Astra 6, Opus 5.5），共进行了 9,136 次尝试。任务分为两个轨道：正确性轨道（从零开始或基于脚手架实现 RTL）和 PPA 轨道（在几乎固定的面积下加速正确的设计）。评估工具链包括 lint、编译、仿真、形式化检查和综合。
- **Evaluation 结果**：
    - **整体排名**：Sol 5.6 和 Fable 5.1 表现优于 Astra 6 和 Opus 5.5。这一排序在所有 200 次随机拆分中保持一致。
    - **成功率**：在正确性轨道中，Sol 5.6 的接受率为 24.5%，Fable 5.1 为 25.0%；而 Astra 6 和 Opus 5.5 分别仅为 16.8% 和 16.5%。
    - **PPA 优化难度**：超过三分之一的尝试未能成功加速正确的设计。在 PPA 轨道中，Sol 5.6 的改进率为 62.4%，显著高于其他模型。
- **对比结论**：相比于仅依赖输出反馈的传统方法，引入状态感知的反馈机制显著提升了 Agent 的性能和效率，证明了当前硬件设计 Agent 亟需能够暴露内部状态的调试支持。

#### 总结
AIChipBench 揭示了 LLM Agent 在设计具有状态依赖性的硬件（如 LLM 解码器）时面临的主要困难在于内部状态的正确维护。文章证明，传统的仅基于输出的测试是不够的，必须引入能够指出具体状态不匹配位置的调试反馈，并使用远超开发规模的严格保留测试集进行最终评估。Sol 5.6 和 Fable 5.1 在此类复杂硬件设计任务中表现最佳，但整体成功率仍有提升空间，强调了未来基准测试需要更关注状态完整性和泛化能力。
