## 1. What the Paper Does
- **Background**: Large language model (LLM) agents are evolving from simple request-response assistants into long-running software actors. They require maintaining state across model calls, forking subtasks, waiting for external events, requesting human authority, generating tools, and performing side effects that must be resumable and auditable.
- **Why Existing Work Falls Short**: Dominant frameworks (e.g., ReAct, AutoGen) typically use a "chat loop + model-facing tool registry" abstraction. This conflates action visibility with resource authority, where tool schemas visible to the model often directly map to wrappers with host filesystem, network, or credential access. This design, which treats tool dispatch as the trust boundary, is fragile against indirect prompt injection, tool-output injection, and dynamic permission requirements for long-lived agents.

## Core Contributions
- **Proposed Agent libOS**: A library-OS-inspired runtime substrate that treats an agent as an "AgentProcess" with identity, lifecycle, and explicit capabilities, rather than a simple conversational thread.
- **Challenge 1: Ambiguous Trust Boundaries Leading to Security Risks**. In existing systems, model-called tool interfaces directly expose host resource permissions, making it difficult to prevent malicious injections or privilege abuse. **Solution**: Agent libOS establishes the rule that "runtime primitives are the authority boundary." Tools are treated as libc-like wrappers, and checks based on explicit capabilities and policies are enforced at primitive boundaries (e.g., filesystem access, object operations), isolating model intent from actual resource access.
- **Challenge 2: Difficulty in State Management and Recovery for Long-Running Agents**. Long-running agents need to handle sleep, interrupts, human approval, and state persistence, which traditional chat loops manage poorly. **Solution**: Introduces the AgentProcess concept, providing process identity, parent-child lineage, typed Object Memory, checkpoints, event queues, and audit records. This supports async scheduling, namespace isolation, and deterministic recovery, allowing agents to be scheduled and audited like OS processes.

## Implementation and Evaluation
- **Implementation**: A Python prototype was implemented featuring async scheduling, namespace-local Object Memory, runtime-integrated human approval, one-shot permission grants, per-process working directories, shell and image-registration primitives. It also includes Deno/TypeScript JIT tools via a libOS syscall broker, filesystem/object bridge tools, and an injectable Resource Provider Substrate.
- **Evaluation Results**: The paper focuses on safety-oriented evaluation rather than planner accuracy. The prototype passed 123 regression tests and includes deterministic demos and real-model smoke scripts. The evaluation demonstrates that the runtime can schedule, authorize, resume, and audit long-running LLM agents without treating tool dispatch as the trust boundary.
- **Comparison**: Unlike traditional frameworks that rely on fragile wrapper conventions for permission separation, Agent libOS addresses system-level issues (identity, scheduling, resource authority, interrupts, isolation, recovery, audit) through system-level capability control and primitive boundary checks.

## 4. Conclusion
Agent libOS proposes a new paradigm for LLM agent runtimes by leveraging OS-inspired process and capability models to address core pain points in security and state management for long-running agents. It liberates agents from simple chat loops, granting them clear identity, lifecycle, and fine-grained permission control, providing a robust foundation for building secure, auditable, and complex interactive long-running LLM agents.
