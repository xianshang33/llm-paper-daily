## 1. What the Paper Does
- **Background**: Analytical workloads in modern data stacks (e.g., DuckDB, Spark, GPU-accelerated frameworks) often need to read data from external relational databases (e.g., PostgreSQL, MySQL). However, traditional data access is entirely guarded by database drivers (like JDBC/ODBC), forcing data through the database engine's query execution layer, network serialization, and client-side deserialization.
- **Limitations of Existing Work**: Existing optimizations (e.g., ConnectorX, federated query systems like XDB/Wayang) still rely on wire protocols for data transfer. Studies show that over 85% of time is spent on client-side deserialization and format conversion, not query execution or network transfer. This architecture creates severe latency and throughput bottlenecks and prevents the use of zero-copy columnar memory formats (like Apache Arrow), as the database server remains the sole gatekeeper of storage.

## Core Contributions
- **Proposed Jailbreak**: A system that bypasses the database engine entirely by directly reading storage files and materializing data as in-memory columnar buffers, leveraging LLM-assisted code synthesis.
- **Challenge 1: Database storage file formats are complex and opaque, traditionally requiring extensive human-engineered parsing logic.**
  - **Difficulty**: Structures like PostgreSQL heap files or MySQL InnoDB pages are complex, making manual parser development costly and error-prone.
  - **Solution**: Jailbreak uses Large Language Models (LLMs) to ingest source code, documentation, and header files to automatically regenerate operator-specific table reading components, turning opaque formats into directly queryable artifacts without human-written parsers.
- **Challenge 2: Ensuring the generated reader outputs standard columnar formats with high performance while maintaining data correctness.**
  - **Difficulty**: Directly reading low-level files requires precise mapping to in-memory Apache Arrow formats for downstream engine compatibility, without parsing errors.
  - **Solution**: Jailbreak generates readers that materialize data directly into Apache Arrow buffers, consumable by engines like DuckDB, Spark, and cuDF. Correctness is validated against JDBC/ODBC baselines across all TPC-H benchmark queries.

## Implementation and Evaluation
- **Implementation & Deployment**: Evaluated on PostgreSQL and MySQL storage files, targeting analytical snapshot scenarios common in read replicas and offline pipelines. The generated readers produce Apache Arrow buffers compatible with major query engines, including GPU-accelerated frameworks (cuDF, Spark RAPIDS).
- **Evaluation Results**:
  - **Correctness**: Data results are identical to JDBC/ODBC baselines across all TPC-H queries.
  - **Performance**: Demonstrates significant improvements in end-to-end analytical throughput, achieving up to **27x speedup**.
- **Comparison**: Compared to traditional JDBC/ODBC connectors and wire-protocol-dependent federated query systems, Jailbreak eliminates serialization/deserialization overhead and network protocol bottlenecks, proving the viability of LLM-assisted storage reader synthesis.

## 4. Conclusion
Jailbreak introduces a novel and generalizable methodology that leverages LLMs to understand database source code and documentation, synthesizing high-performance storage readers that bypass the database engine. This approach successfully addresses the serialization and format conversion bottlenecks in traditional data access paths, significantly boosting analytical workload performance (up to 27x) while ensuring correctness. It offers a viable solution for breaking data lock-in not just for PostgreSQL and MySQL, but for any database system where file formats are accessible via documentation or source code.
